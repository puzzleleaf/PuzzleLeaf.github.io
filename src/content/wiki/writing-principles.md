## 어떤 글을 쓰는가

기술을 처음 만난 개발자도 개요를 이해하고, 실제 코드를 따라가며 자신의 프로젝트에 적용할지 판단할 수 있는 글을 쓴다. 기능 목록을 나열하기보다 하나의 입력이 시스템을 통과하는 경로를 설명한다.

첫 적용 사례는 [Pi의 에이전트 하네스 분석](/posts/pi-agent-harness/)이다. 아래 원칙은 그 글을 작성하며 마련한 초판이며, 이후 글에서 개선할 수 있다.

## 기본 구성

1. **개요**: 무엇인지, 어떤 문제를 해결하는지, 누구에게 유용한지 설명한다. 핵심 용어는 처음 나올 때 풀어 쓴다.
2. **분석 기준과 범위**: 답하려는 질문, 선택한 기준, 읽은 코드, 기준 날짜·버전·커밋과 제외한 범위를 공개한다.
3. **동작 경로**: 입력 → 상태 → 처리 → 결과를 작은 사례로 따라간다. 필요한 코드만 발췌하거나 설명용 의사코드를 쓴다.
4. **움직이는 사례**: 독자의 관심사에 맞는 구체적인 작업을 만들고, 요청과 결과가 오가는 동작을 장면으로 보여 준다. 개념 설명은 본문에 두고, 장면에는 등장인물·요청·처리·결과와 간단한 재생 조작을 둔다.
5. **설계 판단과 적용**: 코드에서 보이는 선택을 근거로 장점, 비용, 적합한 조건을 설명한다. 다른 설계를 제안한다면 작성자의 제안으로 표시한다.
6. **검증과 한계**: 실제로 실행한 범위와 소스만 읽은 범위를 구분한다.
7. **출처**: 맨 아래에 원본 저장소, 핵심 소스, 공식 문서를 모은다. 중요한 주장에는 본문에도 근거 링크를 붙인다.

## 근거를 다루는 방법

저장소를 분석할 때는 움직이는 `main` 대신 커밋 SHA를 고정한다. 핵심 함수는 해당 커밋의 파일과 라인으로 연결한다. 확인 날짜와 커밋 날짜가 다르면 각각의 의미를 분명히 한다.

**관찰**은 코드나 문서에서 확인한 동작이다. **해석**은 그 동작이 어떤 설계상의 의미를 갖는지에 대한 판단이다. **제안**은 다른 프로젝트에 적용하기 위한 작성자의 선택이다. 셋을 한 문장에 섞어 원작자의 의도로 단정하지 않는다.

코드를 그대로 가져오면 발췌라고 밝히고 출처를 붙인다. 수정·단순화한 코드는 의사코드나 응용 예제라고 표시한다. API 예제에는 인증·버전·작업 디렉터리 등 필요한 조건을 적는다. 측정하지 않은 속도, 비용, 정확도는 수치로 만들지 않는다.

굵은 강조는 실제 렌더링도 확인한다. 괄호·기호로 끝나는 문구에 한글 조사가 바로 이어지면 Markdown의 별표 구문이 그대로 보일 수 있다. 이런 경우에는 `<strong>하네스(harness)</strong>라고`처럼 명시적인 HTML 강조를 사용한다. 발행 전에 코드 예시 밖에 `**`가 남아 있는지 확인한다.

## 학습서처럼 설명하기

본문은 부드러운 존댓말을 사용한다. 작은 상황 → 쉬운 말로 역할 설명 → 그림 → 실제 함수·코드 → 의미 되짚기 순서로 안내한다. “경계를 소유한다”, “상태를 투영한다” 같은 추상적인 표현은 구체적인 동작으로 풀어 쓴다. 설명을 쉽게 한다고 서로 다른 개념을 같다고 쓰지는 않는다.

낯선 용어는 처음 등장할 때 일상적인 뜻을 붙인다. 비유는 역할을 떠올리는 데만 사용하고, 실제 동작으로 연결해 준다. 문단마다 관찰·해석 꼬리표를 붙이기보다 “코드에서 확인한 동작입니다”, “여기서 얻은 제 해석입니다”처럼 흐름 안에서 구분한다.

중요한 구조 앞에는 한눈에 읽는 그림을 배치한다. 원고지·노트처럼 은은한 격자, 여백, 작은 선 그림과 둥근 도형을 사용하되 본문의 가독성을 우선한다. 그림은 한 가지 개념만 설명하고, 과한 장식이나 작은 글씨로 복잡하게 만들지 않는다. 화살표 방향과 역할은 원본 소스와 대조하고, 단순화한 부분은 캡션에 밝힌다.

정적인 그림을 본 뒤 같은 개념을 구체적인 작업으로 보여 주는 장면으로 이어 간다. 앞에서는 사례의 상황을, 뒤에서는 기술 구조와 어떻게 대응하는지 본문으로 설명한다. 그림 속 글자는 가능하면 선택·검색할 수 있는 텍스트로 남기고, 모바일에서는 순서를 유지하며 세로로 배치한다.

라이브러리 분석에서는 장면마다 대응하는 실제 함수와 고정 소스 링크를 붙인다. 이야기에서 관찰할 동작 → 해당 구현 → 재사용할 수 있는 처리 → 앱이 직접 맡을 정책까지 연결한다. 일반적인 에이전트 개념을 설명하는 것과 분석 대상 라이브러리의 장점을 입증하는 것을 구분한다. 장점은 요구가 바뀔 때 고칠 부분과 계속 사용할 부분을 구체적으로 설명하고, 측정하지 않은 성능 우열이나 자동으로 제공하지 않는 기능을 덧붙이지 않는다.

움직이는 장면에서도 현재 단계와 소스 연결을 함께 갱신한다. 제공 라이브러리·직접 구현·모델 판단·외부 도구 내부 실행을 라벨과 색으로 구분한다. 라이브러리가 제공하는 단계는 실제 함수·파일·줄 번호를 강조하고, 직접 구현할 단계는 작성할 함수와 라이브러리 연결점을 구분한다. 모델의 판단이나 외부 도구 내부 구현을 라이브러리 소스가 제공하는 것처럼 표시하지 않는다. 소스 링크에 초점을 옮기거나 누르면 현재 단계에서 멈춰 읽을 수 있게 한다.

개발자용 흐름도에는 라이브러리가 제공하는 단계와 프로젝트에서 구현할 단계를 색과 텍스트 라벨로 함께 구분한다. 제공 단계는 실제 함수·파일·고정 커밋의 소스로 연결하고, 앱 단계에는 구현할 역할과 라이브러리 연결점을 적는다. 가상의 앱 함수·파일 이름을 실제 저장소의 코드처럼 연결하지 않는다. 정상 경로뿐 아니라 도구 거절·오류·중단과 반복 경로도 구분하고, 생략한 흐름은 캡션에 밝힌다.

적용 절에서는 “내 프로젝트의 어디에 붙일까”에 답한다. 이미 있는 업무 코드, 새로 만들 연결 코드, 처음 완수할 작업과 확인할 결과를 구체적으로 적는다. 실제 확인한 프로젝트를 사례로 삼되 아직 구현하지 않은 구조는 적용 제안이라고 밝힌다. 도입하지 않아도 되는 조건과 기능을 더할 근거도 함께 설명한다.

라이브러리 없이 직접 연결하는 경우도 같은 사례와 요구로 비교한다. 고정 순서의 작은 스크립트에 필요 없는 판단 모델·실행 루프를 억지로 더해 비교하지 않는다. 모델이 다음 행동을 선택하는 같은 요구를 비교할 때는 직접 만들 공통 코드가 어느 제공 함수로 대체되는지 흐름도에서 나란히 표시하고, 두 방식 모두 남는 업무 코드도 드러낸다. 코드 줄 수를 측정하지 않았다면 감소량을 수치로 주장하지 않는다.

비교 흐름도를 재생할 때는 같은 작업의 현재 단계를 두 경로에서 함께 강조한다. 직접 작성할 코드와 대응하는 실제 라이브러리 함수·소스 위치를 짝으로 보여 주고, 모델 판단이나 공통 업무 코드는 라이브러리가 대신하는 부분과 구분한다. 작은 화면에서도 현재 코드 짝을 함께 읽을 수 있게 배치하고, 소스 링크를 읽는 동안에는 두 경로를 같은 단계에서 멈춘다.

최소 코드 비교도 같은 요구와 도구 계약으로 맞춘다. 공통 작업 명세와 실행 계약은 접을 수 있게 두고, 직접 만드는 루프와 라이브러리 진입점을 나란히 보여 준다. 라이브러리 쪽에만 필요한 등록·설정·정리 코드를 공통 코드로 숨기지 않는다. 직접 정의한 어댑터 계약과 실제 라이브러리 API, 생략한 구현과 실행 검증 범위를 분명히 적는다.

## 인터랙티브 자료의 기준

설계 팁을 다룰 때는 처음 넣을 구성, 뒤로 미룰 기능, 추가가 필요해지는 조건을 함께 적는다. 프로젝트가 선언한 철학과 작성자가 해석한 장점을 구분한다. “작다”, “과하지 않다”는 표현에는 코드의 양, 기본 기능의 범위, 실행과 업무 정책의 분리 중 무엇을 뜻하는지 붙인다. 최소 구성에서도 필요한 관찰·중단·권한·작업 한도를 생략하는 것으로 설명하지 않는다.

각 자료는 독자가 적용하고 싶은 작업의 동작을 보여 준다. Pi 글에서는 검색 태그 필터처럼 구체적인 기능을 Codex가 구현하고 Claude Code가 리뷰하는 과정을 사례로 삼는다. 리뷰 지적 → 보완 → 재검토에서 사용 화면이 어떻게 달라지는지도 보여 준다. 모델 호출과 기존 코딩 도구 호출을 구분하고, 아직 구현하지 않은 연결 코드나 연출한 응답을 실제 연동처럼 표현하지 않는다. 독자에게 로컬 서버를 열거나 설정 파일을 편집하게 하는 개발 실습으로 바꾸지 않는다.

화면에 들어온 장면은 자동으로 반복 재생하고, 결과를 읽을 짧은 간격을 둔다. 화면 밖·백그라운드에서는 멈추고, 동작 줄이기 설정에서는 수동으로만 재생한다. 멈춤·재생·처음으로를 제공하며, 사용자가 멈춘 선택은 화면을 오가도 유지한다. 검토 도구·작업 기준 전달·실행 실패 같은 조건은 재생 중에도 바꿀 수 있게 한다. 자료 안에는 강의식 설명 패널보다 실제 사례의 요청, 상태 변화와 결과를 둔다. 기술 용어와의 대응은 앞뒤 본문에서 설명한다.

직접 만든 사례와 실제 서비스 실행 여부는 본문의 검증 범위에서 구분한다. 장면마다 “시뮬레이션·실행 없음” 같은 라벨을 반복해서 붙이지 않는다. 재생되는 대사를 실제 AI의 응답으로 표현하거나, 연출한 지연을 성능 측정값처럼 쓰지 않는다. 자동 재생의 화면 변화는 보조 기술로 반복 낭독하지 않게 하고, 키보드, 작은 화면, 밝은·어두운 테마를 고려한다. JavaScript가 없어도 이야기의 요청과 결과를 읽을 수 있게 남긴다.

시각 자료의 복잡도가 설명보다 커지면 줄인다. 정적인 관계는 표나 흐름도로 충분할 수 있다. 모든 절마다 애니메이션을 넣는 것을 목표로 삼지 않는다.

## AI를 사용하는 방법

AI는 자료 탐색, 코드 경로 정리, 문장 초안, 시뮬레이션 구현을 보조할 수 있다. AI가 만든 설명도 원본 소스와 대조한다. 실행하지 않은 실험을 수행한 것처럼 쓰거나, 독자가 확인할 수 없는 경험담을 만들지 않는다.

비밀 키·개인 정보·비공개 코드를 예제와 로그에 포함하지 않는다. 소스 분석의 자동화와 실제 도구 실행 권한은 별도로 판단한다.

## 발행 전 확인

- 개요만 읽어도 대상과 글의 질문을 이해할 수 있는가?
- 처음 나오는 용어를 풀었고, 장면의 역할을 읽은 뒤 코드 이름으로 넘어갈 수 있는가?
- 분석 기준과 고정 커밋, 검증 범위가 명시되어 있는가?
- 주장과 연결된 소스가 실제로 그 동작을 보여 주는가?
- 개발자용 흐름도에서 제공 코드와 직접 구현할 코드, 해당 소스와 연결점을 구별할 수 있는가?
- 내 프로젝트에 처음 붙일 작업과 구현 범위, 아직 검증하지 않은 제안이 구체적인가?
- 시뮬레이션과 실제 실행 결과가 구분되어 있는가?
